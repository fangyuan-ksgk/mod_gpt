# R1 / R3 / R5 — interpretability of DLR abstraction codes (Qwen3-0.6B, v9 residual steering)

Checkpoint: `ckpt/arith_v9_paperhp` — six-digit addition + subtraction, one code per answer digit, 30-code codebook.
All numbers below are regenerated by the scripts in `amir_interp_rebuttal/repro/` from static JSON in `amir_interp_rebuttal/results/`.
Determinism check (`repro/determinism.sh`): **PASS** — all five tables byte-identical across two runs and across cwds.

**Verdict.** Only 7 of 30 codes are ever active. One code (6) is genuinely selective:
it predicts `US` (carry cascade through a sum-9 run) at 78% purity, 6.2x lift. Code 17 is
weakly selective for `UB` (44% purity, 4.1x). The remaining five codes sit between 1.2x and
2.2x lift with purity at or barely above the marginal — they are close to uninformative.
Median lift over active codes is 1.62. So: one clean concept, one half-clean concept, five
codes that mostly just say "a digit goes here".

## R3 — position locking

```

  R3 | position locking of active codes | ckpt/arith_v9_paperhp | n_eval=2600 problems x 7 answer positions
  ┌────────┬──────────┬───────────┬────────────────┬────────┬──────────┬────────────────┐
  │   Code │  n fires │   Top pos │  #pos occupied │   of 7 │  PosConc │  Cover@top_pos │
  ├────────┼──────────┼───────────┼────────────────┼────────┼──────────┼────────────────┤
  │      0 │     5200 │         0 │              2 │      7 │    0.500 │         100.0% │
  │     11 │     1163 │         1 │              1 │      7 │    1.000 │          44.7% │
  │     17 │     1026 │         1 │              1 │      7 │    1.000 │          39.5% │
  │      6 │      415 │         1 │              2 │      7 │    0.990 │          15.8% │
  │      2 │     5200 │         2 │              2 │      7 │    0.500 │         100.0% │
  │      7 │     2579 │         3 │              1 │      7 │    1.000 │          99.2% │
  │      1 │     2596 │         4 │              1 │      7 │    1.000 │          99.8% │
  └────────┴──────────┴───────────┴────────────────┴────────┴──────────┴────────────────┘

  Codes occupying exactly 1 position : 4 / 7
  Codes occupying exactly 2 positions: 3 / 7
  Codes occupying 3+ positions       : 0 / 7

  Inverse view -- codes whose top_pos is that position (share = fires_at_top_pos / n_eval):
  ┌──────────┬─────────┬────────────────────────────────────────┬─────────────┐
  │ Ans pos  │ #codes  │ codes peaking here (share of pos)      │ accounted   │
  ├──────────┼─────────┼────────────────────────────────────────┼─────────────┤
  │ 0        │ 1       │ c0 100%                                │ 100%        │
  │ 1        │ 3       │ c11 45%, c17 39%, c6 16%               │ 100%        │
  │ 2        │ 1       │ c2 100%                                │ 100%        │
  │ 3        │ 1       │ c7 99%                                 │ 99%         │
  │ 4        │ 1       │ c1 100%                                │ 100%        │
  │ 5        │ 0       │ (no code peaks here)                   │ 0%          │
  │ 6        │ 0       │ (no code peaks here)                   │ 0%          │
  └──────────┴─────────┴────────────────────────────────────────┴─────────────┘

  Positions covered ~100% by a SINGLE code (code is a constant of position, not
  a function of the input): 0, 2, 3, 4
  Positions with >1 competing code (code can carry input-dependent info): 1
  Positions with no peaking code: 5, 6
  -> these are the off-peak half of the 2-position codes c0, c2 (pos_concentration=0.5),
     but this JSON stores only top_pos, so the exact code->second-position pairing
     is NOT recoverable from results/ alone. Not guessed here.

```

**Verdict — the claim holds, but it is not the good news it looks like.**

Counts: **4 / 7 codes occupy exactly 1 of the 7 answer positions, 3 / 7 occupy exactly 2, and 0 occupy 3 or more.**
Every active code is confined to at most two answer positions, so "codes are locked to one or
two answer positions" is literally true.

The problem is what the locking is made of. Read the inverse view: positions 0, 2, 3, 4 are each
covered ~100% by a *single* code (c0, c2, c7, c1 respectively). At those positions the code is a
constant of the position — it fires on essentially every one of the 2600 eval problems and
therefore carries zero information about the input. Codes 0 and 2 each fire 5200 times with
pos_concentration exactly 0.500, i.e. 2600 firings at each of two positions: a perfect
position tag, not a content detector. Position 1 is the only place where more than one code
competes (c11 45%, c17 39%, c6 16%), and so the only position where the code can depend on the
problem at all.

So the honest statement is: **the code is a deterministic function of answer position at 6 of the
7 positions, and input-dependent at exactly 1 position.** "Position-locked" is true; "position-locked
*and* content-selective" is true only at position 1. If the intended claim was that each code
specialises to a digit place *and* a subtask, the data supports the digit-place half and, for six
of seven places, refutes the subtask half.

Caveat on the data itself: `arithmetic_r1r2.json` stores only `top_pos`, `n_positions` and
`pos_concentration`, not the full position histogram. Positions 5 and 6 have no code peaking at
them; they must be the off-peak halves of c0 and c2 (the only codes with pos_concentration 0.5),
but which of the two goes where is not recoverable from `results/` alone, and the script does not
guess.

> **Reconciliation with the deliverable.** The R3 analysis above is written as
> a defect report, and on reflection that framing over-reads it. Two things:
>
> 1. The codes it calls "position tags" (c0, c2, c7, c1 — the ones covering a
>    position ~100%) are exactly the **generalists** of Finding #6. That
>    specialists and high-frequency near-chance generalists coexist is the
>    paper's claim, and it is what this table shows: 3 specialists carrying
>    14.3% of firings at 2.2–6.2× lift, 4 generalists carrying 85.7% at
>    1.2–1.6×. Read that way this is a replication, not a failure.
> 2. Concentration is not by itself disqualifying, because the *labels* are
>    position-bound: `US` is structurally impossible at d0 and d6, `UD` at four
>    of seven positions. A correct detector for a position-bound condition must
>    be position-bound, so conditioning on position divides out the signal it is
>    meant to validate. See the label-position table in
>    [REBUTTAL_arithmetic.md](REBUTTAL_arithmetic.md).
>
> R3 is not claimed as a finding in either deliverable. This section is retained
> as the working analysis behind Finding #6.

## R5 — sum-9 / equal-digit selectivity

```

  R5 | sum-9 (add) and equal-operand-digit (sub) selectivity | ckpt/arith_v9_paperhp
  Base rates pooled over ALL sampled firings: P(sum9)=23/91=0.253   P(eq)=13/91=0.143
  ┌───────┬──────────┬──────────┬─────────┬───────────┬──────────┬────────┬─────────┬──────────┬─────────┬────────┬─────────┐

  (answer_pos 0 has no operand column, so it is dropped). p = exact one-sided binomial
  P(X >= k) against the pooled base rate; the pool INCLUDES the code being tested, so
  these p-values are conservative for high-rate codes and anti-conservative nowhere.

  │     0 │       3 │            0.274 │     0.00 │            0.131 │     2.18 │
  └───────┴─────────┴──────────────────┴──────────┴──────────────────┴──────────┘

  (ME/UD) is only meaningful for those; every rate above rests on <= 14 examples.

```

**Verdict — one real hit, everything else null, and the sample is tiny.**

**Code 6 is selective for the sum-9 condition.** 11 of its 14 sampled firings have
column_sum == 9 (78.6%) against a pooled base rate of 23/91 = 25.3%; exact one-sided binomial
p < 1e-4, and p stays < 1e-4 against the leave-one-out base of 15.6% (lift 5.0). With n=14 the
95% Clopper-Pearson interval on 11/14 is roughly [49%, 95%], so the point estimate is soft but
the effect direction is not in doubt. Code 6 fires 415 times and only at answer position 1.

**No other code is selective on either condition.** Every other sum-9 rate is *below* the base
rate (lifts 0.00-0.85, all p > 0.7). For equal operand digits, the largest apparent effect is
code 1 at 4/14 = 28.6% (lift 2.0, p = 0.13) and code 0 at 2/7 = 28.6% (lift 2.0, p = 0.26) —
both are two-to-four-example effects and neither survives the most casual scepticism. There is
**no code that marks the subtraction equal-digit (ME/UD) boundary**. Note also that the equal-digit
condition is only meaningful for subtraction, and the per-code subtraction counts are 0-11 of 14;
code 6, the one selective code, has zero subtraction examples in its sample.

**Two honesty flags on the code-6 result:**
1. *It is not independent of R1.* Code 6's top subtask in R1 is already `US` (carry cascade through
   a sum-9 run) at 78% purity. `US` is defined by sum-9 columns, so R5 is largely a re-measurement
   of the same fact on a 14-example subsample, not fresh confirmation. Take it as a consistency
   check, not a second piece of evidence.
2. *It is causally inert.* Knockout (below) shows that zeroing all abstraction codes changes
   arithmetic accuracy by +0.15pp. A code can be a clean read-out of "this column sums to 9"
   while contributing nothing to the computation, and that is what the knockout says is happening.

The base rate itself deserves a note: 25.3% pooled is far above the 10% you would get from random
digit pairs, because the pool is dominated by these seven codes' own firings and code 6 contributes
11 of the 23 sum-9 cases. That is why the leave-one-out column is reported alongside.

## Appendix — code knockout (causal test)

> **Superseded.** The knockout numbers this appendix used to carry were all
> *decode-only* ablations on `scale=0.1` checkpoints, and the conclusion drawn
> from them ("whatever the codes encode, the model is not using it") is no
> longer correct. A scale sweep produced `ckpt/codenet_s0.5_i10_z1_L8_n4000`,
> where a full four-arm knockout shows the codes **are** load-bearing:
>
> ```
>   codes ON   17.50%      RANDOM  11.13%      OFF_full  10.62%
>   removing the codes costs 6.87pp = 39.3% relative
> ```
>
> The `RANDOM` arm accounts for 6.37 of those 6.87 points, so it is code
> *identity* that carries the information, not steering magnitude. See
> [REBUTTAL_codenet.md](REBUTTAL_codenet.md) and `repro/knockout.sh`.
>
> The arithmetic knockout on `ckpt/arith_v9_paperhp` remains ~0 (+0.15pp), and a
> four-rung escalation raised it ~11× without opening the gate — see the
> escalation table in [REBUTTAL_arithmetic.md](REBUTTAL_arithmetic.md) and
> `repro/f2_escalation.sh`. The R1/R3/R5 tables above are claims about what the
> codes *encode* and do not depend on causal load.

## Provenance

This file used to embed a frozen provenance snapshot (commit hash + sha256 per
table). It drifted: two of the JSONs it listed
(`codenet_125step_knockout.json`, `codenet_20k_knockout.json`) no longer exist,
and its commit was recorded as DIRTY. A snapshot that goes stale silently is
worse than no snapshot, so it is generated on demand instead:

```bash
bash amir_interp_rebuttal/repro/manifest.sh
```

That prints the current commit, and for every reported table the script, the
source JSON, its sha256 and the checkpoint. `repro/verify_claims.sh` separately
re-derives each headline number from its source JSON, and `repro/determinism.sh`
runs every table twice and fails on any byte-level drift.

script reads only the static JSON under `amir_interp_rebuttal/results/`.
